# 넷플릭스 · 구글 인증 일정 대시보드

개발 PL이 인증 의뢰를 **예약**하고, 테스터가 **일정·진행·결과**를 공유하는 사내 웹 대시보드.

- 백엔드: Node.js + Express + better-sqlite3 (파일 DB `data.db`)
- 프런트: 정적 HTML/CSS/JS (빌드 단계 없음)
- 뷰: **현황 보드**(상태별 칸반) · **일정표**(일정순 테이블) · **캘린더**(월간) · **일일보고 / 주간보고** · **인증 통계**(모델 × 인증 × Test 목적) · **QE 리소스**(담당자별 업무량) · 병목 경고 위젯 · 등록/상세 모달
- 현황 보드는 상태 칼럼당 카드 **5개까지만** 표시하고 초과분은 `+N개 더보기 / 접기` 토글로 접음
- 상단 **요약 위젯**: 전체/대기·진행/완료/지연/평균 소요일/테스터 부하
- 역할: **의뢰자 / 테스터** 토글로 편집 영역 분리 (이름 입력 시 변경 이력에 기록)
- **변경 이력**: 의뢰별 등록·수정·삭제 기록(작업자·시각·내용)
- **이메일 알림**: 예약확정·완료 시 (config.json 설정 시)
- **일일/주간 현황보고**: 완료 모델 Pass/Fail 현황, Fail은 진행/결과 코멘트 첨부, 진행중·완료 건수 정리. 화면 확인 + **매일 오후 7시 자동 메일**(config.json 설정 시)
- **자동 백업**: `data.db`를 매일 1회 `backups/`로 사본(최근 14개 보관)

## 데이터 항목
| 영역 | 항목 |
|------|------|
| 의뢰 정보 (개발 PL) | 인증종류(Netflix NTS / Google xTS / Amazon AVTS), Test type(IR/LR/MR/파생), Test 목적(3PL/Official/Pre-Test/양산/self/MR + 직접입력), 진행차수(자동 산출·수정 가능), 모델명(드롭다운+직접입력), FW 버전, 의뢰자(드롭다운+직접입력), 희망일정, 비고 |
| 진행/결과 (테스터) | 예약확정 일정, 시작 일정, 완료 일정, **잔여 slot**(비우면 자동 차감), 담당 테스터(드롭다운+직접입력), 상태, 판정(Pass/Fail/Drop), 진행사항, 결과 코멘트 |

모델명은 **이전에 한 번이라도 입력된 값**이 드롭다운으로 뜨고(중복은 `DISTINCT`로 제거), 목록에 없는 값은 그대로 직접 입력하면 된다.

`Test 목적`과 `담당 테스터`는 드롭다운에서 **`+ 직접 입력`**을 고르면 옆에 입력칸이 열려 목록에 없는 값을 쓸 수 있다. 직접 입력한 Test 목적은 **한 번 저장되면 다음 의뢰부터 드롭다운에 자동으로 뜬다**(모델명과 동일하게 `DISTINCT` 조회, `/api/options`). 기본 목록 뒤·`+ 직접 입력` 앞에 붙고, 인증 통계에서 별도 행으로 잡히며 진행차수 산출 키로도 그대로 쓰인다. 담당 테스터는 기존대로 누적되지 않는다.

상태 흐름: `예약대기 → 예약확정 → 진행중 → 완료 / 보류 / 중단` (확정·시작·완료 시각 자동 기록 → 평균 소요일 산출). 완료 건은 보드·일정표에서 **`진행차수 3차, Pass`** 형태의 배지로 표시(Pass 파란색 · Fail 빨간색).

## 인증 통계 (모델별)
**인증 통계** 탭에서 **모델 × 인증종류 × Test 목적**별로 다음을 집계한다. 상단에서 **주간(월~금)**과 **전체 누적**을 전환하고, 주간 모드에서는 `‹ 8/24~8/28 ›`로 주를 넘긴다(대상 기간은 `2026-08-24 ~ 2026-08-28 (월~금)`로 함께 표기). **⤓ 엑셀 다운로드**는 화면에 보이는 집계를 그대로 CSV(UTF-8 BOM)로 내려받는다 — 파일명 `인증통계_2026-08-24_2026-08-28.csv`, 첫 줄에 대상 기간, 마지막 줄에 합계.

| 지표 | 정의 |
|------|------|
| 결과 | 그 조합의 **최신 판정** — `Pass`는 파란 볼드, `Fail`은 빨간 음영 + 흰 볼드 |
| Test 목적 | 3PL / Official / Pre-Test / 양산 / self / MR |
| 진행차수 | **최신 판정 건의 `Round`** (Round 미입력 시 판정 건수로 대체) |
| Pass / Fail | 판정별 건수 |
| Pass율 / Fail율 | **판정 완료 건수** 대비 비율 |

> **미판정 건은 집계 대상에서 제외**하므로 분모는 판정이 끝난 건수이고 **Pass율 + Fail율 = 100%**다. 판정 건이 0이면 비율은 0%로 반환한다(0 나눗셈 방어).

같은 집계를 **주간보고** 하단에 `모델별 인증 현황` 섹션으로 분리해 싣는다. 이 섹션만 **해당 주차 월~금** 기준이고, 주간보고 본문(완료·진행중 집계)은 기존대로 월~일이다. 주차 포함 여부는 시작일~완료일 구간이 주차와 겹치는지로 판정한다.

## 진행차수 자동 산출
의뢰요청 폼에서 **모델명**과 **Test 목적**이 정해지면 `GET /api/next-round`를 호출해 진행차수를 자동으로 채운다. 조회 중에는 스피너가 돌고 입력이 잠겨 중복 입력을 막는다.

| 직전 이력 | 산출 |
|-----------|------|
| 직전 판정이 `Fail` | 직전 차수 **+ 1** (3차 Fail → **4차**) |
| 직전 판정이 `Pass` | **1차** (새 사이클 시작) |
| 판정 이력 없음 | **1차** |

- 이력 조회 키는 **(모델명 × Test 목적)**이며 인증종류는 조건에 넣지 않는다.
- 판정이 끝난 건(Pass/Fail)만 이력으로 센다. 미판정 건은 차수에 영향을 주지 않는다.
- 산출값은 **제안일 뿐이라 직접 수정할 수 있고**, 한 번 손으로 고치면 이후 자동값이 덮어쓰지 않는다.
- 입력칸 옆 **ⓘ**를 누르면 `왜 4차인지`를 이전 차수 타임라인(차수 · 결과 · 일자 · 코멘트)으로 보여준다.

## 병목 경고 위젯
현황 보드 상단에 리스크 건을 끌어올린다. 없으면 위젯 자체가 숨는다.

| 경고 | 기준 (기본값) |
|------|---------------|
| 반복 Fail | 최신 판정이 `Fail`이면서 진행차수 **5차 이상** |
| 장기 미판정 | 판정 없이 **14일**을 넘긴 채 종료되지 않은 건 (클릭 시 상세 열림) |

임계값은 `GET /api/bottlenecks?round=5&days=14`로 조정한다. Pass로 끝난 조합은 반복 Fail 경고에서 빠진다.

## QE 전체 리소스 현황
**QE 리소스** 탭에서 인증 담당 4명(**이은경 · 조아라 · 이해찬 · 문유림**)의 리소스를 5개 위젯으로 본다.

> **메인(현황 보드) 상단에는 `실시간 리소스 가동률`만 둔다.** 나머지 네 위젯은 QE 리소스 탭에서 확인한다. 메인 위젯을 클릭하면 탭으로 넘어간다.

| # | 위젯 | 무엇을 보는가 |
|---|------|--------------|
| 1 | **실시간 리소스 가동률** | 1일 총 가용 slot 대비 오늘 점유율(프로그레스 바) + **잔여 가용 slot**(강조) |
| 2 | **팀원별 업무 부하도** | 개인별 할당 slot 바 + 신호등(안정/주의/초과) |
| 3 | **진행 상태별 파이프라인** | 예약대기·예약확정·진행중 건수/slot + **가장 오래 대기 중인 건** |
| 4 | **인증 타입별 점유 현황** | 도넛 차트로 NTS·ATVS·xTS가 리소스를 얼마나 먹는지 |
| 5 | **스마트 알림** | 초과 할당 · 리소스 충돌 · 일정 밀림 · **리소스 확보 예정(D-N)** |

그 아래에 `인증 담당 리소스 상세`(주간 가용 기준 지표 · 일별 가용 현황 · 담당자별 할당)와 `기타 테스터 리소스`가 이어진다.

- **`1 slot` = 1명의 1일 업무량**(person-day). 담당자에게 쌓인 slot 합계가 곧 **그 사람의 소요 영업일수**다.
- **대상**은 상태가 `예약대기 · 예약확정 · 진행중`인 의뢰 전체. 완료·보류·중단은 남은 업무량이 아니므로 제외한다.
- **리소스 풀이 둘이다.** `인증 담당`(4명)과 `기타 테스터`(김지윤·조진원 등)는 **별도 리소스로 관리**하므로 가용·사용률을 섞지 않는다. 기타 물량이 인증 담당 풀의 100%에 섞이면 사용률이 왜곡된다.
- **각 풀의 1주 가용을 100%로 산정한다.** 인증 담당은 `4명 × 5 영업일 = 20 slot`, 기타는 `기타 인원 × 5 slot`이 각각 100%다.
- 영업일은 **주말·공휴일을 제외**한다.
- 담당자별 리소스는 자동 할당으로 채워질 예정이므로 **여유(빈 slot)** 를 중심으로 본다.
- **자동 할당 대상은 인증 담당 풀뿐이다.** 담당자 미정 건은 인증 담당 4명에게만 `배정예정`으로 채워지고, 기타 풀에는 배정예정이 없다.

| Test Type | 소요 |
|-----------|------|
| `Google xTS` — IR · LR | **3 slot** |
| `Google xTS` — MR · 파생 | **2 slot** |
| `Netflix NTS` — IR · LR · MR · 파생 | **12 slot** |
| `Amazon AVTS` (작업지시서 `ATVS`) | **4 slot** |

`Google xTS`는 MR·파생만 2이고 나머지는 3이다 — `test_type`이 빈 구 데이터를 2로 세면 물량이 과소평가된다. **규칙에 없는 인증종류는 0으로 세지 않고 `미정의`로 모아 화면에 경고**한다.

### 진행률 반영 — 리소스는 `잔여`로 계상한다
위 표는 **계획 소요**다. 이미 진행한 만큼은 남은 업무량이 아니므로 빼고 계산한다.

- **자동 차감** — `시작일`이 있으면 `시작일 ~ 기준일 직전`의 경과 영업일수를 소화분으로 본다. **기준일 당일은 아직 진행 중이라 소화로 세지 않는다**(시작일 == 기준일이면 소화 0, 잔여는 전량).
- **수동 보정** — 의뢰 상세의 `잔여 slot`에 값을 넣으면 자동 계산을 이긴다. 계획 소요를 넘거나 음수면 범위로 잘라낸다.
- **예정 초과 진행** — 소화분이 계획을 넘으면 **잔여를 0으로 만들지 않고 최소 1로 남긴다.** 진행중인 건이 리소스에서 조용히 사라지면 안 되기 때문이다. 초과분은 `예정 초과 진행` 알림으로 따로 낸다.
- 총계·담당자별·일별 배치·타입 분포가 **모두 잔여 기준**이다. 계획 소요는 `plan_slots`로 보존해 `계획 12 · 소화 10 · 잔여 2 (83%)`로 함께 보여준다.

> 이 반영 전에는 두 달 전 착수한 4 slot 건도 오늘부터 4일을 다시 점유한다고 계산했다. 잔여로 바꾸면서 그런 건은 잔여 1 + `19일 초과 진행` 알림으로 드러난다.

### 1. 실시간 리소스 가동률
**메인에 노출되는 유일한 리소스 지표다.**

- 분모는 **팀 전체의 1일 총 가용 slot** = 인원수(4) — 한 사람은 하루 1 slot을 쓴다.
- 분자는 **오늘 담당자를 점유 중인 확정 업무**(`진행중` · `예약확정`)의 수. **`예약대기`는 아직 확정 전이라 가동률에서 뺀다**(파이프라인에서 따로 본다).
- **잔여 가용 slot**을 크게 강조한다 — 신규 의뢰를 즉시 수용할 수 있는 수치다. 여유 담당자 이름을 함께 적는다.
- 보조로 **이번 주** 가용/사용/여유를 붙인다(공휴일이 든 주는 가용이 줄어든다).
- 색은 80% 미만 파랑 / 80~100% 주황 / 100% 이상 빨강.

### 2. 팀원별 업무 부하도 (신호등)
개인별 할당 slot을 바 차트로 그리고, **1인 주간 가용 5 slot** 대비 사용률로 신호등을 매긴다. 눈금이 가용 100% 위치다.

| 신호 | 기준 | 뜻 |
|------|------|-----|
| 🟢 **안정** | ≤ 80% | 적정 수준 |
| 🟡 **주의** | ≤ 100% | 가용 한도 임박 |
| 🔴 **초과** | > 100% | 초과 할당 (예: NTS 12 slot + xTS 3 slot = 300%) |

### 3. 진행 상태별 파이프라인
`예약대기` · `예약확정` · `진행중` 3개 카드에 **건수 · 총 slot · 담당 미정 건수**를 담는다. 세 단계 slot 합은 인증 담당 풀 물량과 일치한다(테스트로 고정).

아래에 **가장 오래 대기 중인 건**을 최대 2개 노출한다 — `예약대기` 상태로 등록 후 며칠 지났는지, 희망일이 이미 지났는지(`경과`)를 함께 적어 최우선 배정 대상을 드러낸다. 14일 초과는 빨간 배지다.

### 4. 인증 타입별 점유 현황
도넛 차트 + 표로 `NTS(12) · ATVS(4) · xTS IR/LR(3) · xTS MR/파생(2)`이 전체 리소스에서 차지하는 비중을 본다. **특정 시기에 무거운 인증이 몰렸는지** 판단하는 영역이다. 건이 없는 타입은 표시하지 않고, 비중 합은 100%다.

### 5. 스마트 알림
| 알림 | 감지 방식 |
|------|-----------|
| **초과 할당** | 담당자 사용률이 100%를 넘긴 경우 |
| **리소스 충돌** | 같은 담당자의 **계획 일정**이 서로 겹치는 조합. 직렬 배치는 겹침을 자동으로 밀어내므로 배치 결과가 아니라 배치 전 계획 구간으로 판정한다 |
| **예정 초과 진행** | 소화분이 계획 소요를 넘긴 건. 잔여를 1 slot으로 붙잡고 있다는 신호이기도 하다 |
| **일정 밀림** | 직렬 배치 결과가 계획일보다 늦게 착수하는 건 (충돌의 결과). 지연 일수 순, 최대 5건 |
| **리소스 확보 예정** | 담당자가 busy → idle로 바뀌는 첫 시점. `D-2: 이해찬 리소스 확보 예정` 형태로 D-day 순 노출 |

리스크가 없으면 위젯이 비어 있다고 명시한다 — 거짓 경보를 만들지 않는다.

### 풀별 요약 — 1주 가용 기준 정량 현황 (담당자 이름 없음)
`인증 담당 리소스` / `기타 테스터 리소스` 두 섹션에 같은 지표가 각각 붙는다. 기타 인원이 없으면 그 섹션은 뜨지 않는다.

| 지표 | 정의 |
|------|------|
| 1주 가용 (100%) | `그 풀의 인원수 × 5 영업일`. 인증 담당은 **20 slot** |
| 미완 소요 | 그 풀에 속한 의뢰의 slot 합계 |
| 사용률 | `미완 ÷ 1주 가용` (%). 100%를 넘으면 1주에 못 끝난다 |
| 여유 / 초과 | 100% 미만이면 `여유 N% (N slot 배정 가능)`, 넘으면 `초과 N% (N slot 넘침)` |
| 소요 주수 | `미완 ÷ 1주 가용` (주). `2.4주`처럼 읽는다 |
| 미배정 | 담당 테스터가 비어 있는 물량 (인증 담당 풀에만 있다) |
| 소진 예상 / 완료일 | 그 풀 인원이 전부 투입될 때 필요한 영업일수와 그 날짜 |

머리말에 **두 풀을 합친 전체 물량**(건수 · slot)을 함께 적는다.

### 일별 가용 리소스 현황
풀마다 향후 20 영업일(기본, `?days=`로 5~60)에 대해 **날짜별 가용 / 배정 / 배정예정 / 여유 / 사용률**을 보여주고, 주 단위 소계를 얹는다. 공휴일이 든 주는 영업일이 줄어 **가용도 함께 줄어든다** (추석 주 → 영업일 3일 × 4명 = 12 slot).

배치 규칙은 이렇다.

- **한 담당자는 하루 1 slot만 쓴다**(직렬). 그래서 의뢰를 담당자별로 줄 세워 영업일에 이어 붙인다. 시작은 `max(대표 일정, 기준일)`이다.
- **`배정예정`** 은 담당 테스터가 없는 건을 **가장 빨리 비는 담당자 자리에 채워 본 자동 할당 미리보기**다. 실제 배정이 아니라 예측이므로 색을 달리 표시한다. **인증 담당 풀에만 있다** — 기타 테스터는 별도 리소스라 자동 할당 대상이 아니다.
- 각 날짜에 **그날 비어 있는 담당자**를 흐린 칩으로 함께 보여준다 — 자동 할당이 어디에 넣을 수 있는지가 바로 보인다.
- 조회 구간을 넘어간 물량은 `overflow`로 표기한다. 각 풀에서 **배치분 + 구간초과 = 풀 물량**, 그리고 **두 풀 합 = 전체 물량**이 항상 성립하도록 테스트로 고정했다. 어느 쪽에도 속하지 않은 물량이 생기면 화면에 집계 오류로 경고한다.

### 세부내용 — 담당자별 리소스 할당
| 컬럼 | 정의 |
|------|------|
| 할당 slot / 주간 가용 | 쌓인 slot 합계 / 1인 주간 가용 **5 slot** |
| 소요 영업일 | 할당 slot과 같다 (`1 slot = 1일`) |
| 예상 소진일 | 오늘부터 세어 **할당 slot번째 영업일** |
| 여유 / 초과 | `N slot 여유 (배정 가능)` / `N slot 초과 (다음 주로 밀림)` |
| 가용 대비 사용률 | 100% 눈금이 찍힌 막대. 넘으면 넘친 만큼 빨강 |

- **미배정**은 담당 테스터가 비어 있는 건. 인증 담당 풀 표 아래 `미배정 — 자동 할당 대상` 행으로 분리하되 **그 풀 합계에 포함**한다. 사람이 없어 개인 가용 개념이 없으므로 사용률은 `—`다.
- **기타 테스터도 사람이 있으니 주간 가용 5 slot을 갖는다.** 자기 풀의 표에서 사용률·여유/초과를 그대로 본다.
- 담당자 행 아래 `건별 상세`를 펼치면 그 slot이 어느 의뢰에서 왔는지(일정·인증종류·모델명·차수·적용 규칙)를 볼 수 있다.

조회는 `GET /api/resources` (`?as_of=YYYY-MM-DD` 기준일, `?days=N` 일별 구간). 응답은 `totals`/`daily`/`rows`(인증 담당)와 `others_totals`/`others_daily`/`others`(기타)로 갈리고, `overall`에 두 풀 합계가 담긴다.

### 공휴일 관리 — ⚠ 목록 검증은 사람이 한다
영업일 계산에 쓰는 공휴일은 `holidays.js` **코드 상수**다(사내망이라 외부 API를 호출하지 않는다). 음력 기반 공휴일(설·추석·부처님오신날)과 대체공휴일은 정부 관보로 확정되는 값이므로, **운용 전에 상수 목록을 공고와 대조해야 한다.**

사내 지정 휴일이나 정상근무 전환은 `config.json`에서 덮어쓴다.

```json
"holidays": {
  "add":    ["2026-11-13"],
  "remove": ["2026-05-01"]
}
```

계산 결과가 상수에 없는 연도로 넘어가면 화면에 **주말만 제외한 값이라는 경고**가 뜬다. 그 연도 공휴일을 `holidays.add`에 넣으면 사라진다.

> 이미 운영 중인 서버를 최신 코드로 업데이트할 때는 아래 대신 **[DEPLOY.md](DEPLOY.md)**(재배포 가이드)를 따른다. 아래 절차는 처음 설치할 때만 쓴다.

- **서버**: Mac Mini, 사내 IP `172.16.3.136`
- **운영 포트**: `3001`
- **접속 주소**: `http://172.16.3.136:3001`

1. 프로젝트를 Mac Mini로 복사 (git clone 또는 폴더 복사). `node_modules`, `data.db`는 제외.
2. 의존성 설치 및 기동:
   ```bash
   cd cert-schedule-dashboard
   npm install
   PORT=3001 HOST=0.0.0.0 npm start
   ```
3. 같은 사내망 PC 브라우저에서 접속: `http://172.16.3.136:3001`
4. macOS 방화벽이 켜져 있으면 node의 들어오는 연결을 허용 (시스템 설정 → 네트워크 → 방화벽 → 옵션에서 node 허용).

### 상시 구동 (재부팅·크래시 자동 복구) — launchd 권장
`~/Library/LaunchAgents/com.qa.cert-dashboard.plist` 생성:

<?xml version="1.0" encoding="UTF-8"?>

## 이메일 알림 설정 (선택)
`config.json`이 없으면 알림은 자동으로 생략되고 앱은 정상 동작합니다. 사용하려면:

1. 예시 파일 복사: `cp config.example.json config.json`
2. `config.json`을 열어 Gmail 정보 입력:
   - `smtp.user` / `smtp.pass`: 보내는 Gmail 계정과 **앱 비밀번호 16자리**
     (Google 계정 → 보안 → 2단계 인증 → 앱 비밀번호에서 발급. 일반 로그인 비번 아님)
   - `notifyTo`: 상태변경 알림(예약확정·완료)을 받을 메일 주소 목록 (테스터·PL 등)
   - `reportTo`: 보고 메일을 받을 주소 목록. 생략하면 기본값 `keonhee.cho@kaongroup.com` 하나로 발송. **사외 개인계정은 넣지 마세요**
   - `baseUrl`: `http://172.16.3.136:3001`
3. 서버 재시작. 기동 로그에 `[notify] 이메일 알림 활성화`가 보이면 적용됨.

> 상태변경 알림: 의뢰 상태가 **예약확정** 또는 **완료**로 바뀔 때 `notifyTo` 전원에게 발송.
> `config.json`은 비밀번호를 담으므로 git에 올리지 않습니다(.gitignore 처리됨).

메일 본문은 **완료·Pass·Fail·진행중 건수 같은 집계 수치와 대시보드 링크**뿐입니다.

미출시 모델명과 인증 결함 내용, 직원 실명이 사외 메일함(Gmail 등 외부 사업자 인프라)에 사본으로 남는 것을 막기 위한 조치입니다. 상세 내용은 사내망 대시보드에서만 볼 수 있습니다.

- 코드상 화면용 본문은 `html`, 발송용 본문은 `mailHtml`로 분리돼 있습니다.
- 링크 주소는 `config.baseUrl`을 씁니다. 없으면 링크 대신 안내 문구가 나갑니다.
